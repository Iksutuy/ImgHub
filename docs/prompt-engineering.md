## 一、总览页的 8 个维度

用户给定的框架，逐条扩充为「写什么 + 怎么写才对 + 常见错误」：

| # | 维度 | 核心问题 | 关键要点 |
|---|---|---|---|
| ① | **主题** Subject | 谁 / 什么 | 具体到可辨识；人物要交代取景与动作（`full body visible, feet included`） |
| ② | **媒介** Medium | 以什么形式 | 照片/插画/雕塑…；要写实就明确写 `photorealistic`；镜头参数只当**外观线索** |
| ③ | **环境** Environment | 在哪里 | 给环境结构（前/中/背景）；要虚化就说明；编辑时最易被越界 |
| ④ | **灯光** Lighting | 什么类型 | 写**方向与时机**（午后侧向自然光透过落地窗）；冷暖对比制造张力 |
| ⑤ | **颜色** Color | 什么色调 | 点名主色并说明分布；胶片感/颗粒属同维度 |
| ⑥ | **情绪** Mood | 唤起什么感受 | 别只丢情绪词 —— 说清是什么让画面有这种情绪 |
| ⑦ | **构图** Composition | 如何取景 | 写位置与占比；画幅在**参数里**选、构图在**提示词里**写 |
| ⑧ | **风格与约束** | 收口 | 风格词克制；描述内容而非下指令；编辑必写「保留清单」 |

> 总览页里还有「怎么用这份清单」与「三条通用检查（出图前自问）」两节。

## 二、为什么必须按端点分开（不是一个"通用提示词"）

同一句需求，两个端点偏好的写法**不一样**，一套通用规则必然在某一边出错：

| 维度 | OpenAI（GPT Image） | 千问（Qwen-Image） |
|---|---|---|
| 核心方法论 | 官方 8 条 prompting 基本功（定义结果 / 只描述看得见的 / 引号写文字 / 分开写改与保） | 官方**协议层硬约束** + 示例结构 |
| 长度 | 无硬性短限（prompt 上限 32000 字符） | **约 800 Token（2.0 系 1300）超出自动截断** |
| 结构 | 可用分段/类 JSON，鼓励按「场景→主体→细节→约束」组织 | **只能一个 text**，多条会报错 |
| 语言 | 无特别要求 | 官方只正式支持**简体中文与英文**，其他不确定 |
| 负向约束 | 没有独立字段 → 写进正文（Do not add ...） | 有 **`negative_prompt` 独立字段** → 不该塞进正文 |
| 编辑重点 | 反复强调 "Do not change ..." 的保留清单 | 指定输入图角色 → 禁止改动项 → 再描述要改的 |
| 多图 | 给参考图分配角色（编号 + 用途） | **输出比例以最后一张为准**，顺序有语义 |

**结论**：润色时若一律用 OpenAI 那套，千问用户会拿到动辄超 800 Token 的提示词
（**被静默截断**，关键约束丢失），或把「不要 XX」写在正文里而没走 `negative_prompt`；
反过来，千问那套给 OpenAI 用又会过度压缩、丢掉官方鼓励的分段与细节描述。

## 三、润色用哪一套：自动 + 可覆盖

`PolishService.EffectiveStyle`：

```
Style = "auto"（默认） → 跟随**当前生图 provider**
      = "openai"        → 强制用 OpenAI 那套
      = "qwen"          → 强制用千问那套
```

⚠️ **为什么 auto 跟随"生图 provider"而不是"润色端点"**：
润色端点是用户自配的任意 OpenAI 兼容 chat 端点，它只负责"把话写清楚"，
**和最终要喂给哪个生图模型无关**。真正决定提示词该怎么写的是生图模型。
（润色端点 ≠ 生图端点，两者是独立的配置。）

UI 上：
- 润色浮窗顶部有「提示词风格」下拉（自动 / OpenAI / 千问），可随时覆盖；
- 切生图 provider 时 `ActiveStyle` 自动更新（`MainViewModel.OnProviderChanged`）。

## 四、两个端点的指南要点（浮窗内容摘要）

### OpenAI（GPT Image）—— 来源 `docs/GPT Image prompting.md`

**八条基本功**（官方 "Prompting fundamentals"）：

1. 先定义结果：点名主体与用途，写清构图、画幅、位置约束；复杂需求按
   场景 → 主体 → 细节 → 约束 分段；
2. 选可维护的格式（短句/段落/类 JSON/指令/标签都行，挑最好读好改的）；
3. 只描述看得见的东西（材质、光线、颜色、媒介）；要写实就明确写 `photorealistic`；
4. 说清人和动作（`full body visible, feet included`、视线方向、与物体的交互）；
5. 要精确文字就**加引号** + 说明位置与字体 + 补一句"不要其他文字"；
6. **把「要改的」和「要保的」分开写**（edit 场景的核心）；
7. 给参考图**分配角色**（编号 + 用途：主体/风格/服装/背景）；
8. 一次只改一件事，重复关键约束。

**官方反复强调**：编辑永远同时交代"保持不变的是什么"；暗光/雨夜/霓虹场景要写
尺度、氛围、颜色而不是情绪词；文字密集场景把 quality 调到 medium/high 再比。

### 千问（Qwen-Image）—— 来源 `docs/千问-*.md`

**协议层硬约束**（写提示词时就要照顾）：

- 只支持简体中文与英文；
- 文生图 2.0 系 1300 Token，其余约 800 Token，**超出自动截断**；
- 只能一个 text（"不传或传入多个将报错"）；
- 多图输入时**输出比例以最后一张为准**；
- "不要 XX" 走 `negative_prompt`（官方常用值：「低分辨率，低画质，肢体畸形，
  画面过饱和，人脸无细节，过度光滑，AI 感」）。

**编辑（I2I）结构**（官方示例的骨架）：

1. 指定每张输入图的角色（「使用图一的城市照片作为底图」）；
2. 明确**禁止改动**的部分（「请勿更改照片中的真实建筑、街道、车辆或人物。保持照片的真实性。」）；
3. 再描述要加入/修改的内容，连同**画法、风格、位置、大小**（官方示例会写到
   「约占画面高度 1/10」这种精度）。

## 五、指南数据为什么要放 Core

`PromptGuide` 放在 `ImgHub.Core`（而不是 XAML 里写死）的理由：

1. 这些文案是**行为契约**（对应官方文档的明确说法），要能被单测断言
   （见 `tests/ImgHub.Core.Tests/PromptEngineeringTests.cs` 的"内容不串端点"测试）；
2. 浮窗内容与"润色用哪套 prompt"必须共用同一份"哪个端点"的定义
   （`PromptGuide.For(provider)`），否则两处会漂移 —— 指南讲 OpenAI、实际发千问的风格。

⚠️ **最怕的错是两页内容串了**。测试用各自文档里**独有**的硬事实做指纹：
OpenAI 页必须出现 `photorealistic` / `change only X` 且**不**出现 `1300 Token`；
千问页必须出现 `简体中文` / `800 Token` / `自动截断` / `最后一张` 且**不**出现 `photorealistic`。

## 七、改动检查清单

改提示词相关逻辑时逐条核对：

1. `PromptGuide` 两页是否有内容串端点（跑 `PromptEngineeringTests` 的指纹测试）；
2. `PolishService` 的 4 个端点专用 prompt（`SysOpenAi*` / `SysQwen*`）是否都还在被
   `PickSystem` 引用（删旧 prompt 时容易漏改分派）；
3. 千问那套是否仍带着"长度上限/单 text/negative_prompt"三条硬约束；
4. 跑 `dotnet test tests\ImgHub.Core.Tests`（离线、不花钱）。
